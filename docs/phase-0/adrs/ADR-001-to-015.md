# Initial Architecture Decision Record Set

Status: Accepted as Phase 0 baseline, subject to later superseding ADRs with explicit approval.

Each ADR below records the approved V1 decision and its primary consequence.

## ADR-001 — Modular core vs microservices
Decision: use a strongly modular transactional core; extract services only when scale/team/availability evidence justifies it. Consequence: domain ownership and interfaces are mandatory even inside one deployable API.

## ADR-002 — Four separately deployable web surfaces
Decision: Student, Institution, Employer, and Operations experiences are distinct web surfaces sharing design/system packages. Consequence: privileged Operations concerns are not mixed into ordinary portal navigation/authorization.

## ADR-003 — PostgreSQL system of record
Decision: use PostgreSQL-compatible managed relational storage for authoritative transactional data. Consequence: schema ownership, migrations, constraints, and transaction boundaries are first-class.

## ADR-004 — RBAC plus scoped/temporal ABAC
Decision: roles are insufficient alone; authorize organization, relationship, resource, time, consent, and assignment scope server-side. Consequence: authorization policy/test infrastructure is foundational.

## ADR-005 — Student-owned longitudinal career identity
Decision: student identity/history continues across institution changes; institution visibility is relationship-scoped and time-bounded. Consequence: no permanent single `college_id` authorization model.

## ADR-006 — Managed identity provider
Decision: prefer managed authentication/identity over custom password/token infrastructure; final provider is benchmark/UX/cost gated. Consequence: application owns authorization and memberships, not credential security primitives.

## ADR-007 — REST plus asynchronous events
Decision: REST for synchronous product operations and versioned events for side effects/integration. Consequence: API/event compatibility conventions apply from V1.

## ADR-008 — Durable queue plus transactional outbox
Decision: reliable asynchronous side effects use durable queues and outbox/idempotent consumer patterns. Consequence: notifications, document jobs, AI async work and integrations tolerate retries/duplicates.

## ADR-009 — Provider-independent AI Gateway
Decision: all LLM/model access goes through an internal gateway/orchestrator. Consequence: portals/domains cannot call model providers directly.

## ADR-010 — Managed inference first
Decision: begin with managed/pay-per-use inference; self-hosting requires measured quality/latency/privacy/cost advantage. Consequence: no always-on GPU EC2 dependency in V1 architecture.

## ADR-011 — Private object storage/quarantine document pipeline
Decision: uploads are private, quarantined, scanned, then promoted to approved storage state. Consequence: uploaded documents never become public object URLs by default.

## ADR-012 — Versioned deterministic readiness scoring
Decision: readiness is reproducible from published versioned rules/weights; LLM text is not the numerical authority. Consequence: every historical score stores scoring model/version and component explanation.

## ADR-013 — Employer accountability/material-term versioning
Decision: material opportunity terms are versioned and disputes are evidence-based. Consequence: affected applicants can be notified of changed terms and moderation can compare original vs changed promises.

## ADR-014 — Private AI conversations excluded from institution/employer visibility
Decision: raw student AI chats are private by default and are not used as hidden employability/morality scores. Consequence: authorized structured career outcomes may be shared separately without exposing raw conversations.

## ADR-015 — Single-region Multi-AZ V1
Decision: use one AWS region with Multi-AZ managed services and tested recovery rather than active-active multi-region. Consequence: invest in backup/restore, RPO/RTO testing, and horizontal service scaling before global HA complexity.

## ADR lifecycle

Future ADRs use: Context, Decision, Alternatives, Security/Privacy Impact, Operational Impact, Consequences, Migration/Rollback, Status, Date, Approvers, and Supersedes/Superseded-by fields. Material changes to these decisions require Product/Architecture approval.
